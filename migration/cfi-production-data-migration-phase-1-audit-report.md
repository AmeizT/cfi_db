# CFI Production Data Migration — Phase 1 Read-Only Backend Audit

Audit date: 2026-08-20  
Scope: current backend worktree, Django migration files, available Git history, and read-only queries against the local SQLite development database.  
Production/Neon: not accessed.

## Executive conclusion

The migration is feasible, but implementation should not begin until the blockers in this report are resolved.

The canonical monthly container is `reports.AssemblyReport`. Its intended identity is an assembly plus a canonical first/last day pair for one calendar month. The database only enforces uniqueness on the exact tuple `(assembly, period_start, period_end)`; it does not enforce that the dates are canonical month boundaries. The local database already contains two one-day reports, demonstrating that the current constraint is not equivalent to “one report per assembly/month.”

The current report contract has six sections:

1. General Attendance
2. Sunday School Attendance
3. Tithes
4. Revenue
5. Operating Expenses
6. Activity & Other Expenses

The report lifecycle reads these sections by assembly and date range, not consistently by Report foreign key. This makes a correct `assembly + month` derivation possible for most records, but it also allows a wrong or missing Report FK to be hidden from some report views.

The most important blockers are:

- Attendance has four incompatible headcount calculations, and the current save hook overwrites normalized historical totals from gender-split fields that did not historically exist.
- Sunday School has no Report FK and no start-date guard. Its absence is distinguishable only by absence of rows, while the local database already contains two pre-launch records.
- `Income` and `FixedExpenditure` each fan out into multiple new rows. There is no legacy-ID field or migration ledger, and the target uniqueness constraints make a naive rerun unsafe.
- Several finance categories do not have an exact approved mapping. `remittance` and `investment` are especially unsafe to classify automatically.
- Local data shows partial old/new finance overlap, wrong-period links, stale stored totals, and duplicate candidates. Production must be inspected with the same read-only verifier after backup.

No application code, model, migration, configuration, or data was changed during this audit. The only created artifact is this report.

## Evidence and limitations

- Static inspection covered models, serializers, services, views, filters, managers, signals, save/delete hooks, migrations, tests, and all management-command directories under `backend/cfidb/apps`.
- The local database was queried only with `sqlite3 -readonly`. No Django management command was run.
- The backend is a nested Git repository with a very large pre-existing dirty worktree. Most of the modern architecture—including Revenue, Overhead, Sunday School, normalized Attendance, and later report lifecycle files—is untracked in that nested repository. Git can establish the original Report-FK introduction, but cannot establish commit history for most current code. Migration `Generated by` comments are recorded below as schema evidence, not as Git commit evidence.
- Local database findings are not claims about production. They demonstrate the exact anomalies that production preflight must test.

### Report

1. A monthly report is intended to be identified by `assembly + calendar month`, represented as `(assembly, period_start, period_end)`.
2. It has date boundaries, not separate month/year columns.
3. The database has `unique_assembly_report_period` on the exact three fields. It does not prevent two differently bounded reports in the same calendar month.
4. Current source models with direct Report FKs are Attendance, Tithe, Revenue, Overhead, Expenditure, legacy Income, and legacy FixedExpenditure. Lifecycle/compliance models also reference Report.
5. Sunday School is expected to contribute to a Report but has no Report FK. Historical Attendance/Tithe/Income/FixedExpenditure/Expenditure records can have a null FK. Revenue/Overhead can also be null at schema level.
6. Every source Report FK is nullable. Delete behavior is `PROTECT` except Expenditure, which is `CASCADE`.
7. Normal creation should use `apps.reports.services.lifecycle.ensure_report()`. It canonicalizes any input date to first/last day, uses `get_or_create`, handles a race via `IntegrityError`, creates all six section-status rows, and writes an audit record for a new Report.
8. `apps.reports.services.report_service.create_report()` is a thin wrapper over `ensure_report()`. FinancialBase, Attendance, Sunday School, and Expenditure call it indirectly. `apps.bookkeeper.services.manual_entry.resolve_report()` duplicates the logic and directly calls `AssemblyReport.objects.create()`, thereby bypassing section initialization and the creation audit.
9. Status is migration-relevant. Source save hooks only permit `draft`; submitted/approved/archived historical reports block normal saves. New historical drafts become overdue and can affect compliance. Report lifecycle also derives a display status from section state and current version rather than relying only on the stored workflow status.
10. Report totals are stored, not database-generated. Section sources and analytics also calculate data dynamically; ReportVersion snapshots freeze totals at submission. Stored and dynamic figures can diverge.

The reusable logic is `report_period()`, `ensure_report()`, `get_section_source()`, `get_report_sections()`, `validate_report()`, `AssemblyReport.calculate_totals()`, and `AssemblyReport.recalculate_attendance_totals()`. A migration command should reuse the canonical period calculation, but should not call row `save()` methods during bulk historical attachment because those methods create Reports, validate draft state, recalculate repeatedly, and audit.

### Attendance

Historical fields remain in the active table: `adults`, `children`, `guest_attendance`, `new_converts`, `altar_call`, and `baptisms`. Migration 0067 added gender-split fields and normalized totals with default zero; it did not include a data migration or a marker saying whether gender detail was collected.

Current calculations are inconsistent:

| Code path | Formula |
|---|---|
| `Attendance.headcount` | `total_adults + total_visitors + online_viewers`; excludes children |
| `get_monthly_summary()` | adults + Sunday School boys/girls + visitors; excludes online viewers |
| `AssemblyReport.recalculate_attendance_totals()` | adults + Sunday School boys/girls + visitors + online viewers |
| `get_section_source(general_attendance)` | adults + legacy `Attendance.children` + visitors + online viewers |
| Report attendance endpoint, per row | adults + Sunday School boys/girls on the same date + visitors + online viewers |

`Attendance.save()` always performs:

```text
total_adults       = men + women
total_visitors     = visitor_men + visitor_women
total_new_converts = new_convert_men + new_convert_women
total_altar_call   = altar_call_men + altar_call_women
total_baptisms     = baptism_men + baptism_women
```

Therefore, copying legacy `adults` into `total_adults` with `QuerySet.update()` is only temporarily safe. Any later model save on that historical row recalculates the value from default-zero gender fields and can erase it. The existing backfill command has exactly this durability problem.

The old stored `headcount` column was removed by migration 0054. Current recalculation does not overwrite an old headcount because that field no longer exists, but it can overwrite the retained legacy component values' normalized representation. Historical legacy component fields themselves are retained and should remain immutable.

### Sunday School

Sunday School counts are calculated properties, not stored totals. `total_children` is boys + girls; visitors and first-timers are separate; `grand_total` includes all three groups. Report attendance totals include only boys + girls, while the Sunday School report section total includes children, visitors, and first-timers.

There is no Report FK. Association is computed from `assembly + service_date`. Saving a row creates the Report and triggers attendance aggregate recalculation. There is no validation or database constraint for the stated start date `2026-09-01`.

The safest historical meaning is: before 2026-09-01, no SundaySchoolAttendance row means “not historically collected.” Do not create zero rows. A numeric zero inside an existing row means an explicitly recorded zero and is not equivalent to absence.

### Finance

New Report totals intentionally ignore legacy Income and FixedExpenditure:

```text
income_total  = Revenue.amount + non-trash Tithe.amount
expense_total = Overhead.amount + Expenditure(price * quantity)
balance       = income_total - expense_total
```

Expenditure is separate from FixedExpenditure and remains part of the new architecture as “Activity & Other Expenses.” It needs Report/date normalization but must not be converted to Overhead.

The legacy APIs remain registered and writable at `/income/` and `/regular_expenditure/`. Legacy summary serializers still calculate from Income and FixedExpenditure, while newer Report calculations use Revenue and Overhead. The cutoff cannot be guaranteed by migration alone; application routing/permissions must prevent post-cutoff writes to the old endpoints.

## Exact finance mappings

### Income to Revenue

One Income row becomes up to four Revenue rows. Zero components should normally produce no target row; otherwise zero-only legacy rows create false activity. The command must still record that the legacy source was evaluated.

| Legacy field | Target | Transformation / decision |
|---|---|---|
| `id` | migration lineage ledger | Required for idempotency; no target field exists. |
| `church_id` | `Revenue.assembly_id` | Direct rename. |
| `timestamp` | `Revenue.timestamp`; derives Report month | Direct if non-null; null is a blocker. |
| `offering` | Revenue amount with distinct `Offering` category | Exact category exists in tests/custom data but not in seeded standards. Standard mapping requires approval. |
| `fundraising` | Revenue amount with distinct `Fundraising` category | Can map to seeded `Fundraising`, preferably through an assembly custom category to preserve source label. |
| `thanksgiving` | Revenue amount with distinct `Thanksgiving` category | No seeded exact standard. Likely `Donations & Gifts`, but requires approval. |
| `donations` | Revenue amount with distinct `Donations` category | Map custom category to seeded `Donations & Gifts`. |
| `total_income` | no row field | Verification only: must equal component sum and migrated Revenue component sum. |
| `notes` | `Revenue.notes` | One-to-many policy needed. Repeating on every component preserves text but duplicates it in reports. |
| `statement` | `Revenue.statement` | Same one-to-many issue. File should be referenced, not copied, unless storage requirements say otherwise. |
| `created_at`, `updated_at` | ledger/audit metadata | Auto fields are not preserved by normal saves. Decide whether lineage metadata is enough. |

Revenue has no creator field. Existing AuditLog cannot reliably represent legacy source identity and should not be used as the only lineage mechanism.

Because Revenue is unique by `(report, category)`, direct use of one broad standard category would collide when, for example, Offering and Donations coexist in a month. Distinct assembly categories mapped to standards preserve both source components. Multiple Income rows in one assembly/month also collide; local data contains one such group. The command must either stop for manual consolidation or aggregate same-month component amounts while preserving many-to-one lineage and attachment metadata.

### FixedExpenditure to Overhead

One FixedExpenditure row becomes one Overhead per nonzero component. Use distinct assembly-specific OverheadTypes for each legacy component, with approved mappings to broader standard categories. Directly using the broad standards would violate unique `(report, overhead_type)` when several legacy components share a standard group.

|---|---|---|
| `rent` | Rent → Facilities & Utilities | High |
| `water` | Water → Facilities & Utilities | High |
| `electricity` | Electricity → Facilities & Utilities | High |
| `wages` | Wages → Staffing & Payroll | High |
| `bank_charges` | Bank Charges → Bank & Professional Fees | High |
| `car_maintenance` | Car Maintenance → Maintenance & Repairs | High |

Expenditure remains Expenditure. Its `timestamp` should be normalized from `invoice_date` when null, and its Report should match that date. Its stored `total` should equal `price * quantity` before and after linking.

### Existing commands

`people/management/commands/backfill_attendance_totals.py` accepts `--cutoff-date` and `--dry-run`, copies legacy fields into normalized totals with `QuerySet.update`, and recalculates already-linked Reports in one transaction. Do not run it as-is because:

- it has no assembly/from/verify-only filters;
- it does not assign missing Reports;
- it does not exclude soft-deleted rows;
- later `Attendance.save()` overwrites its result from gender splits;
- Report child totals come from Sunday School rather than legacy children;
- its transaction can become too large for production.

`bookkeeper/management/commands/backfill_remittances.py` has no dry-run or transaction strategy and filters Tithe by nonexistent field `branch`; it is not reusable without repair.

`backfill_tithes_payment_method.py` performs unconditional updates and does not support dry-run/verification. It is unrelated to report linking and should not be combined with this migration.

No existing command backfills Reports, copies Income to Revenue, copies FixedExpenditure to Overhead, records lineage, or performs full reconciliation.

| MEDIUM | `MonthlyFinanceSnapshot` may disagree with both architectures. | Use as secondary evidence, not an authoritative overwrite source. |
| MEDIUM | Audit behavior can duplicate or use non-choice action spellings through save hooks. | Migration should emit one explicit structured audit/ledger record per action and bypass implicit hooks. |
| LOW | New amount precision is wider (`14,2` versus `10,2`). | No numeric loss expected; still reconcile exact decimals, never floats. |

## Recommended management commands

Every command should default to no writes unless `--apply` is explicit. Support `--dry-run`, `--verify-only`, `--assembly`, `--from`, and `--to`; print a stable run ID and mapping-manifest checksum. Reject overlapping invocations with an advisory lock where PostgreSQL permits.

### `backfill_monthly_reports`

- Inputs: assembly/date range; selected source models; conflict policy; historical workflow status policy.
- Dry run: enumerate canonical `(assembly, month)` obligations, existing canonical Reports, noncanonical overlaps, statuses/versions, and missing section rows.
- Apply: transaction per assembly-month; lock candidate Reports; call/reuse canonical period logic and initialize six section rows idempotently.
- Conflicts: stop on overlapping/noncanonical/multiple Reports. Do not choose `.first()`.
- Rerun: `get_or_create` on canonical tuple; fill only missing section rows; never change submitted snapshots.

### `backfill_report_relationships`

- Scope: Attendance, Tithe, Revenue, Overhead, Expenditure, and optionally retained legacy rows.
- Derivation: required assembly plus authoritative date; Expenditure uses verified timestamp/invoice-date fallback.
- Verification: report assembly and inclusive bounds must match every linked row.
- Apply: `QuerySet.update` in bounded batches to avoid save hooks; transaction per assembly-month.
- Conflicts: null date/assembly, noncanonical Report, non-draft/versioned Report, or uniqueness collision is a hard failure recorded in a conflict export.

### `backfill_finance_models`

- Default range: through 2026-07-31 only. Refuse dates on/after 2026-08-01 unless an exceptional flag is explicitly provided.
- Inputs: versioned YAML/JSON mapping manifest; lineage strategy; zero-row policy; attachment/notes policy.
- Dry run: show source counts and component totals, existing target candidates, category/type creation plan, duplicate source months, and exact conflicts.
- Apply: transaction per assembly-month; lock legacy rows and Report; create categories/types deterministically; bulk-create target rows; write lineage in the same transaction; retain old rows.
- Idempotency: lineage unique key, not fuzzy amount/date/category matching.
- Rerun: skip verified lineage entries; fail if target checksum differs; repair only through an explicit conflict mode.

### `backfill_attendance_headcounts`

Use this name rather than `recalculate_attendance_headcounts`, because historical values must be translated, not blindly recomputed.

- Inputs: approved schema cutoff/version and formulas; default historical upper boundary 2026-08-31 for Sunday School absence semantics.
- Dry run: compare legacy values, gender-derived totals, all current headcount formulas, and affected Reports.
- Apply: preserve legacy fields; set normalized totals according to approved schema marker; create no Sunday School rows; batch update without save hooks; recalculate affected Reports once.
- Rerun: compare stored migration/schema version and expected formula checksum.
- Conflict: any row with both nonzero legacy and contradictory nonzero gender detail needs review, not automatic precedence.

### `verify_historical_migration`

- Must never write.
- Exit nonzero on blocker/high invariant failures.
- Produce machine-readable JSON/CSV plus human summary.
- Support pre-migration baseline capture and post-migration comparison by run ID.
- Include all reconciliation checks below, status/version checks, FK deletion behavior, category review state, and orphaned lineage.

## Idempotency strategy

The safest design is a dedicated migration-lineage model/table, created in the later implementation phase, with at least:

```text
run_id
source_app
source_model
source_pk
source_component       # offering, rent, etc.; blank for one-to-one links
target_app
target_model
target_pk
source_checksum
mapping_version
created_at
```

Enforce uniqueness on `(source_app, source_model, source_pk, source_component, mapping_version)`. Allow multiple source entries to point at one aggregated target if duplicate monthly source rows are deliberately consolidated. Validate that the target still exists and its immutable migration fields/checksum still agree before declaring a rerun successful.

Alternatives are weaker:

- Adding `legacy_income_id`/`legacy_fixed_expenditure_id` to targets needs an additional component key because both migrations are one-to-many.
- Embedding legacy IDs in notes is user-visible, unconstrained, and brittle.
- Generic AuditLog lacks a constrained source-target relation.
- Matching by assembly/date/amount/category produces false positives when legitimate rows share values and cannot distinguish pre-existing manual Revenue/Overhead from migrated rows.

The ledger should be written in the same transaction as targets. A dry run must not create ledger rows.

## Reconciliation strategy

Capture a baseline before writes, then verify at global, assembly-month, and category/component levels.

### Reports and links

- Exactly one canonical Report per assembly/month in scope.
- `period_start` is the first day and `period_end` is the last day of the same month.
- No overlapping noncanonical Report remains unresolved.
- Every in-scope Attendance, active Tithe, Revenue, Overhead, and Expenditure has a Report.
- Every FK matches both assembly and source date.
- Every Report has exactly six unique section statuses.
- Submitted/current-version Reports are unchanged unless explicitly handled by an approved amendment plan.

### Finance

For each assembly/month and then globally:

- Income row count evaluated equals lineage source count, including zero-only rows.
- `SUM(Income.total_income)` equals `SUM(offering + fundraising + thanksgiving + donations)` before migration.
- Component sums equal migrated Revenue sums for the exact mapped component categories.
- FixedExpenditure source row/component counts equal lineage counts.
- `SUM(FixedExpenditure.total)` equals the sum of the 13 fields included by its current save formula.
- Migrated Overhead totals equal those same included components by mapped type.
- Remittance is reconciled separately and must not enter operating-expense equality unless the approved model changes the definition.
- Expenditure row count and `SUM(price * quantity)` are unchanged.
- Old tables remain unchanged by checksum, row count, amount totals, and attachment references.
- No target lacks lineage and no lineage points to a missing/mismatched target.
- Existing unlined pre-cutoff Revenue/Overhead is reported separately, never assumed to be migrated.

### Attendance

- Legacy Attendance fields are unchanged.
- Normalized totals equal the approved formula for that row's schema period.
- No SundaySchoolAttendance exists before 2026-09-01 unless explicitly quarantined as test/error data.
- No migration-created zero Sunday School rows exist.
- For September 2026 onward, valid Sunday School rows satisfy uniqueness and teacher/assembly rules.
- Report stored attendance totals equal the approved period-aware source calculation.
- General Attendance and Sunday School section totals remain separate and are not double-counted.
- Soft-deleted Attendance/Sunday School rows are excluded consistently.

## Recommended migration order

1. Commit/tag the exact backend baseline; resolve migration/code drift.
2. Approve attendance formulas, finance category mapping, remittance handling, attachment policy, historical Report status, and lineage design.
3. Disable or date-gate legacy Income/FixedExpenditure writes from 2026-08-01; enforce Sunday School start date.
4. Take a production backup and restore it to a Neon rehearsal branch/database.
5. Run `verify_historical_migration --verify-only`; export and resolve every blocker/high conflict.
6. Install the lineage schema and deterministic mapping manifest in the rehearsal environment.
7. Canonicalize/create Reports and section rows by assembly-month.
8. Attach current source records (Attendance, Tithe, Revenue, Overhead, Expenditure) without save hooks.
9. Backfill historical Attendance totals under the approved period-aware rule; create no historical Sunday School rows.
10. Copy Income to Revenue and FixedExpenditure to Overhead only through 2026-07-31, retaining old rows and writing lineage atomically.
11. Recalculate each affected Report once, then capture/compare full reconciliation output.
12. Rehearse rerunning every command; the second apply must produce zero new targets and identical totals.
13. Repeat on production only after review/sign-off, with the same baseline manifest and an immediate post-run verifier.
